# Changelog

## Earner withdrawal fee, daily check-in, deploy carry-over

- **Withdrawal fee.** Base rate `money.withdraw_fee_bps` (default 1000 = 10 %) in Admin → Money → Money settings next to the minimum withdrawal (percentage 0–50, two decimals, CSRF, older forms keep the rate, audited `admin.withdrawal_fee_changed` with the rate as target id). Per-level override `earner_levels.withdrawal_fee_bps` in Admin → Growth → Earner levels (empty = base, never above the base — refused on save and capped at runtime if the base is lowered later; audited `admin.level_withdrawal_fee_changed`). With levels off the base applies.
- Confirmed rules: fee = floor(gross × rate / 10000), rounded down in the earner's favour; the withdrawal stores `fee_bps`, `fee_kobo`, `fee_level_id` at request time and nothing recalculates them (admin changes never affect queued withdrawals); pre-0014 withdrawals backfilled to fee 0 / 0 bps and pay in full; a rejected or failed withdrawal returns the full gross amount incl. the fee.
- Earner withdraw page: rate shown on the form; "Preview withdrawal" shows amount / fee / "You will receive" computed on the server (nothing created or held); "Confirm" sends the quoted fee and `Withdrawals::request` recomputes it under the wallet lock — a mismatch (admin change, level change, tampering) creates nothing and re-previews with "The fee changed" (`Payments\WithdrawalFeeChanged`). A single-step POST only previews. Min/max/24-hour limits stay on the gross amount.
- Payout: AfrStar is sent `amount − fee` (as before, now non-zero); paid posting Dr held (gross) / Cr `system:afrstar_clearing` (net) / Cr `system:withdrawal_fees` (fee, new credit-normal revenue account); reject/failed posting unchanged (gross back to available). Wallet list, open-request notice, admin withdrawals list and approve confirmation show fee/net; decline and failure messages say the fee came back.
- **Daily check-in.** Earner dashboard card (streak of consecutive Lagos days, today's status, "Check in" button) posting to `checkin.php` (CSRF, throttled 20/h). Once per Africa/Lagos day — unique `daily_checkins (user_id, lagos_date)` plus the wallet lock; ledger Dr `system:checkin_rewards` (new debit-normal expense) / Cr earner available, type `checkin_reward`, key `checkin:<userId>:<YYYY-MM-DD>` (idempotent; a lost row never pays twice). Pays the earner's level amount `earner_levels.checkin_reward_kobo` (default ₦0 = off for that level, max ₦10,000); needs a confirmed email, an active account and the admin switch `checkin.enabled` (default off) in Admin → Growth → Earner levels (audited `admin.checkin_enabled` / `admin.checkin_disabled`, level changes `admin.level_checkin_reward_changed`). Streak resets to 1 after a missed day. Wallet history "Daily check-in reward"; levels pages list the fee and check-in per level.
- `Core\Clock` (was a placeholder): now, Lagos date, freeze for CLI tests.
- Reconciliation: `Money\Fees::reconcileWithdrawals` and `Growth\Checkin::reconcile` in `Ledger::reconcile`; `database/verify/withdrawal_fee_checkin_reconciliation.sql`. Admin Reports "Paid out" is gross (incl. fees).
- **Deploy.** `scripts/deploy/cpanel-release.sh` copies `mgm-relay.php` and `mgm-forward.php` (configurable: `YOLOTASK_CARRY_PUBLIC_FILES`) from the release `~/public_html` resolves to (fallback `current`) into the new release's `apps/main/public/` before switching `current` (`cp -a`, logged to `runtime/logs/deploy-carry.log`, never fatal), and prints a note while `public_html` is not pointed at `current`. Both names are git-ignored under `/apps/main/public/`. `docs/cpanel-setup.md`: re-point `public_html` to `current/apps/main/public` once.
- Migration `0014_withdrawal_fee_daily_checkin.sql` (additive): `withdrawals.fee_bps`, `withdrawals.fee_level_id` (+ backfill to 0), `earner_levels.withdrawal_fee_bps` (NULL), `earner_levels.checkin_reward_kobo` (0), table `daily_checkins`, accounts `system:withdrawal_fees` and `system:checkin_rewards`, settings `money.withdraw_fee_bps = 1000`, `checkin.enabled = 0`. No new cron lines.

## Advertiser deposit cashback

- Every confirmed AfrStar deposit — the collection callback crediting an order, or an admin crediting a reviewed amount-mismatch AfrStar payment (same two hook points as the referral commission) — pays the depositing advertiser `cashback.rate_bps` of the credited amount, rounded down to the kobo (`intdiv`, like commission), into the same available wallet balance the deposit credited. Deposits below `cashback.min_deposit_kobo` get none (0 = no minimum). Defaults: 0 bps (off) and no minimum.
- Ledger: new debit-normal expense account `system:deposit_cashback`; Dr `system:deposit_cashback` / Cr advertiser available, type `deposit_cashback`, key `cashback:<paymentOrderId>`, description "Deposit cashback X% on top-up <order_sn>". A `deposit_cashbacks` row (unique per payment order: `paid`, `skipped` with reason `off` / `below_minimum` / `account_not_active` / `too_small`, or `reversed`) records the decision, so a redelivered or simultaneous callback, the admin review path and the hourly catch-up pay once. Admin wallet credits, adjustments and bonuses are not payment orders and never earn cashback; cashback is not a payment order, so it never earns referral commission or further cashback. Referral commission on the deposit is unchanged and paid alongside (on the deposit amount only).
- Failure isolation: cashback runs after the deposit commits (after the callback response, like commission); any error is logged (`cashback.failed`) and the deposit stays confirmed. The hourly cron catches up deposits confirmed in the last 48 h that have no cashback decision; older deposits are never revisited, so switching cashback on never pays for past deposits.
- Reversal: no deposit reversal exists in the system; a paid cashback can be reversed by an admin the same way as a referral payout (reason 5–255 characters, Dr advertiser available / Cr `system:deposit_cashback`, key `cashback-reverse:<id>`, refused if the advertiser no longer has the money, audited `admin.cashback_reversed`, advertiser notified).
- Admin → Growth → Referrals: new "Advertiser deposit cashback" card next to the commission settings — percentage 0–50 (up to two decimals, stored as basis points) and minimum deposit in naira (0–₦500,000), CSRF-protected, validated server-side, audited (`admin.settings_updated` plus `admin.cashback_rate_changed` / `admin.cashback_min_deposit_changed` with the new value as target id); list of paid/reversed cashback with the reverse form.
- Advertiser: top-up page shows "Get X% cashback on deposits" and "Minimum top-up for cashback: ₦N" when on (hidden at 0 %); wallet history and receipts show "Deposit cashback X% on top-up <order_sn>" ("Deposit cashback reversed" for a reversal); in-app notification "Deposit cashback: ₦N" (rewards category, no email).
- Reconciliation: expense account = standing cashback, rows match their ledger transactions and key, cashback only on paid top-ups on the credited amount for the depositor, never above 50 % (part of `Money\Ledger::reconcile`; `database/verify/deposit_cashback_reconciliation.sql`).
- Migration `0013_deposit_cashback.sql` (additive): table `deposit_cashbacks`, account `system:deposit_cashback`, settings `cashback.rate_bps = 0`, `cashback.min_deposit_kobo = 0`. Applies straight after 0012 (0010/0011 stay skipped placeholders). No new cron lines (the hourly cron runs the catch-up).
- Tests: `tests/Integration/Growth/cashback_test.py`.

## Phase 7 — Leaderboard and levels page

- Earner leaderboard (`leaderboard.php`, port of V1): This Week / This Month and Top Workers / Top Referrers. Week = Monday 00:00 to now, month = the 1st 00:00 to now, both Lagos time (WAT). Top Workers ranks by tasks approved in the period (by approval time, `submissions.decided_at`) with the rewards those tasks paid; Top Referrers ranks by referral payouts credited in the period (milestone bonuses + advertiser deposit commissions, `referral_payouts.status = 'paid'`; reversed and skipped payouts never count) with their total. Public names are first name + last initial. Staff (reviewers, admins) and suspended/closed accounts are left out; advertisers can appear on Top Referrers. - Earner levels page (`levels.php`): every active level in order with requirements (approved tasks, approval rate) and benefits (tasks held at once, premium tasks — the only benefit fields levels have), current level highlighted, progress bar and exactly what is missing for the next level; reads `earner_levels` live so admin edits show at once; "Levels are paused" when `levels.enabled = 0`. Dashboard: level badge links to it, plus quick-link cards for Leaderboard and Levels (the bottom dock stays as it is).
- Public levels page on the main site (`/levels.php`, linked from the home navigation): active levels and benefits only, no personal data (no session user is read).

- Migration `0012_leaderboard.sql` (additive): indexes `submissions (status, decided_at, earner_user_id)` and `referral_payouts (status, created_at, referrer_user_id)`, table `leaderboard_rewards` (reward history, unique per ledger transaction). ## Referral network allowance + interest targeting

- Referral abuse rule changed: shared networks are normal, so each referrer gets an allowance (`referrals.ip_allowance`, default 3, Admin → Growth → Referrals, 1–100) of referred sign-ups per IP address — the referrer's own IP counts as that IP — and per device (user-agent hash). Sign-ups 1–3 are recorded active and pay as usual; the 4th and later are flagged for admin review (no payout until approved; approval pays what was earned). A sign-up on the referrer's own device (same device and network as one of their sessions in the last 30 days) is always flagged as a likely self-referral. The count covers all earlier referees of that referrer (any status, all time) and runs under a lock on the referrer row. Older admin forms without the field keep the current value; changes are audited (`admin.referral_ip_allowance_changed`).
- Interests: admin-managed list (Admin → Growth → Interests: add, rename, reorder, disable; at least 3 active), 12 seeded for the Nigerian market. Earners choose 1–3 (account → Interests, dashboard and task-feed prompt while none, and right after email confirmation as an onboarding step with "Skip for now"). Every new campaign chooses 1–3 (required, server-side on create/edit/fund; editable by the advertiser while draft or pending approval; admins view and edit them on the campaign page during approval and while live/paused). Mobile-first chip picker with a live counter that locks at 3; CSRF on every form; audited.
- Premium targeting: premium (targeted) tasks are shown in the feed and reservable only for earners whose level allows premium and who share at least one active interest with the campaign — enforced in the feed query and again in the reservation (start) endpoint under the campaign lock; the task page explains why Start is disabled. Earners with no interests see no premium tasks until they choose. Campaigns with no active interest (made before interests existed, or all disabled) match every earner who has chosen interests. Standard tasks are unaffected.
- Migration: folded into `0009_referrals_levels_notifications.sql` (not yet applied on staging): tables `interests`, `user_interests`, `campaign_interests`, setting `referrals.ip_allowance`, referral indexes per referrer. The never-applied placeholder `0002_settings_catalog_interests.sql` was deleted.
- Tests: `tests/Integration/Growth/phase6_test.py` adds the allowance (IP 1–3 accepted and paid, 4th flagged, admin limit change, device allowance, own device) and interests sections; Phase 4/5 suites send an interest with every campaign.

## Phase 6 — Referrals, levels, bonuses and notifications

- Referrals: every earner and advertiser has a code (created on first use); `register.php?ref=CODE` on the earner and advertiser portals records the referrer once at sign-up (remembered for the browser session, never changed later). Not recorded: self-referral by normalised email (lower-case, `+tag` removed, Gmail/Googlemail dots removed) or an alias of any existing account. Sign-ups from the referrer's device/network, or another referee's network (last 30 days), are recorded as **flagged** and earn nothing until an admin approves them (rejected = never pays).
- Referred earners: the referrer earns every active milestone (defaults 10 approved tasks = ₦100, 25 = ₦200; they stack), once per referee, counting approvals made after the referral. Paid right after any approval path commits (advertiser, auto, admin, reviewer stale queue, appeal overturn) and by an hourly catch-up sweep; Dr `system:referral_bonus` / Cr referrer wallet, key `ref-milestone:<referralId>:<milestoneId>`. An admin reversal of an approval never claws back: payouts above the referee's new count are flagged for review.
- Referred advertisers: the referrer earns `referrals.commission_bps` (default 5 %, admin 0–50 %) of every confirmed AfrStar deposit for life — on the collection callback and on an admin review-credit of an AfrStar payment, never on admin wallet credits or bonuses. Dr `system:referral_commission` / Cr referrer wallet, key `ref-commission:<paymentOrderId>`; 0 % rounds to a "skipped" row.
- Referral page for earners and advertisers (links + copy buttons, masked referees, progress to the next milestone, earnings). Admin → Money → Referrals: on/off switch, commission %, milestones add/edit/disable/delete (delete only when never paid), flagged sign-ups (approve/reject with note), payouts with filters and ledger reversal with reason, catch-up button.
- Earner levels (Starter 0, Bronze 50 / 80 %, Silver 200 / 85 %, Gold 500 / 90 %): approved tasks + approval rate set tasks held at once (overrides `tasks.max_active_reservations`) and premium (targeted) feed access. Dashboard badge and progress; Admin → Tasks → Earner levels (edit, add, delete, on/off).
- Admin one-off bonuses from the wallet page (Dr `system:bonuses` / Cr wallet, reason required, user notified).
- Notifications: in-app inbox with a bell and unread count in the earner/advertiser header, list with All/Unread, open, mark read, mark all read; per-category email switches (task results, appeals, top-ups and withdrawals, campaign reviews, referral earnings and bonuses); security emails always sent. Existing emails for rejections, appeals, top-ups, withdrawals and campaign decisions now go through the inbox + switch. Optional OneSignal push behind `config-private/notifications.php` (absent = off).
- Admin announcements (Growth → Announcements): audience all/earners/advertisers, start/end in Lagos time, banner while live (dismissible), one inbox item per user when it starts (five-minute cron), withdraw. Not emailed.
- Crons: daily prunes read notifications older than 90 days; hourly runs the referral catch-up; every five minutes delivers started announcements. No new cron lines.
- Reconciliation: referral expense accounts = standing payouts, payouts match their ledger transactions, commissions only on credited top-ups. `database/verify/referral_award_reconciliation.sql` (was a placeholder) and `pre_release_checks.sql` updated.
- Migration `0009_referrals_levels_notifications.sql` (additive; plain DDL). The old placeholders `0007_growth_referrals_bonuses_levels.sql` and `0008_notifications_announcements.sql` were deleted (superseded) and the later placeholders renumbered to `0010_virtual_number_orders.sql` and `0011_indexes_constraints_finalization.sql`. ## Phase 5 — Appeals and reviewer queues

- Earner appeals: one per rejected proof within 72 h (`appeals.window_hours`), reason required, optional extra screenshot (proof upload rules); not after a resubmission, and appealed proofs cannot be resubmitted. Appeal button/status on the earner submission page; emails on filing and decision. Rejection emails mention the appeal option.
- Reviewer portal: appeal queue (oldest first) with the instructions version used, proofs, rejection reason, earner note and appeal; exclusive 30-minute claims (`reviews.claim_minutes`) with release and expiry; uphold or overturn with a required note. Second queue for stale pending proofs (approve/reject before auto-approve, reviewer recorded as decider). "My decisions" history; reviewer dashboard with live counts; reviewers can open proofs only for appealed or pending submissions.
- Overturn pays through the same approve path (reward hold respected, key `appeal-approve:<id>`). When the escrow has no room the shortfall comes from the advertiser wallet, then from the new `system:advertiser_receivable` account with an advertiser debt for admins (`appeal-fund:<id>`); recorded as over budget (`campaigns.extra_approved_count`, appeal funding columns), never takes another earner's slot. Advertiser emailed; campaign page lists appeal outcomes and appeal top-ups.
- Admin → Tasks → Appeals: all appeals with filters, decide open appeals, override a reviewer once (final, audited; reversing an overturn takes the reward back and returns any top-up), Flagged advertisers (≥ 3 overturned and ≥ 30 % in 30 days, admin-only) and Advertiser debts (collect from wallet / write off). Flags and debts also on the user list and campaign page. Appeal settings on Task settings.
- Reconciliation adds over-budget approvals and receivable = open debts; `database/verify/campaign_funding_reconciliation.sql` updated.
- `cron/every-five-minutes.php` deletes expired reviewer claims; `every-fifteen-minutes.php` reports open appeals. No new cron lines.
- Migration `0008_appeals_reviewer_queue.sql` (additive; plain DDL). Integration test `tests/Integration/Appeals/phase5_test.py`; `run-servers.sh` also starts the reviewer portal on 8404.

## Bank-detail encryption without libsodium

- `Security\Crypto::seal()` now writes `enc2:` (OpenSSL AES-256-GCM, HKDF key with its own context) so saving a bank account works on hosts without ext-sodium (cPanel ea-php84). `reveal()` reads `enc2:`, legacy `enc1:` (only when ext-sodium is loaded; otherwise a clear error) and legacy plain text; `isSealed()` knows both prefixes.
- `scripts/encrypt-bank-details.php`, `database/verify/pre_release_checks.sql` and the 0006 last-4 backfill treat both prefixes as encrypted.
- Admin Money settings shows a bank-encryption readiness check (missing sodium is fine). Display-only paths (admin withdrawals list, wallet history, payout emails) fall back to ••••last4 if a legacy value cannot be decrypted on the host; payout approval still decrypts strictly. Test `tests/Unit/Crypto/crypto_nosodium_test.py`; `run-servers.sh` takes `YT_PHP_ARGS`.

## Phase 3 — Wallets, ledger and AfrStar payments

- Double-entry ledger in integer kobo (`Money\Ledger`): balanced postings only, unique idempotency keys, row locks, no negative wallets; wallet balances cached on `wallets` and `ledger_accounts`.
- One NGN wallet per earner/advertiser (created lazily) with available and held balances; wallet page with history; wallet balance on dashboards and a Wallet item in the bottom dock.
- AfrStar v2 client (`/gateway/payin/`, `/gateway/payout/`, `/gateway/balance/`), MD5 ordered-value signing, configurable base URL; credentials from `config-private/afrstar.key` (`MERCHANT_SN,MERCHANT_AK,MERCHANT_SK`) or `payments.local.php`. Pages say "Payments are not available yet" when not configured.
- Advertiser top-ups: order → AfrStar hosted page → return page that refreshes until confirmed. Credited only by a verified collection callback; amount mismatches go to an admin review queue and are never auto-credited.
- Earner withdrawals: one bank account (full AfrStar bank-code list, 10-digit NUBAN, password re-entry and security email on change), request holds funds, one open withdrawal at a time, admin approve (AfrStar payout) or reject (hold released); payout callback pays out or refunds and emails the earner.
- Public callback endpoints `/hooks/afrstar/collection.php` and `/hooks/afrstar/payout.php` on the main site: raw callbacks logged, `SUCCESS` only after commit, idempotent, non-200 otherwise.
- Admin Money section: wallet totals, live AfrStar balance, reconciliation button, user wallet search, manual credit/debit with mandatory reason (ledgered, audited), withdrawals queue, payment review queue, top-up orders, raw callback log, ledger transactions, money settings (min/max top-up and withdrawal, unpaid-order expiry).
- `cron/daily.php` expires unpaid top-ups after 24 h (no money moves) and runs the reconciliation (exit 2 on mismatch).
- Migrations `0003_wallets_ledger.sql` and `0004_payments_banks_withdrawals.sql` (additive). Integration test `tests/Integration/PaymentCallbacks/phase3_test.py` with a local fake AfrStar gateway.
